## 8. 真实数据流（hand model / view-plan / snapshot / worker）

### 8.1 hand model

```
标注图 (…-labeled.png)  →  颜色标注切出 per-nail mask  →  assets (kind='nail_mask')
                                                       →  hand_model_slots
                                                          (nail_id, hand, finger,
                                                           mask_digest, bbox, area_px)
base 照片 → assets → hand_models.base_digest（尺寸 1448×1086 记在 hand_models 行上）
app_settings: hand_model_{tone}_{view} → base 照片路径
```

mask 语义：**RGBA，指甲在 alpha，RGB 全 0。**
用 `Image.open(p).convert("L")` 读会得到全空 mask —— 必须取 `split()[-1]`。
（本会话第一版测量脚本就是这样错的，10/10 全 empty。）

`p2_open_hands` 屏幕顺序（来自 `matrix_views.json` 的 `screen_slots`，权威）：

```
左手 屏幕左→右: nail-05 nail-04 nail-03 nail-02   拇指 nail-01 (lower-center-left)
右手 屏幕左→右: nail-07 nail-08 nail-09 nail-10   拇指 nail-06 (lower-center-right)
```

p2 与 p4 的左手屏幕顺序**确实相反**（手背 vs 握拳），两者都由 mask 质心验证过。
**让两者一致的「修复」会破坏其中一个 view。**

### 8.2 view-plan

```
styles.plan_image_path (运营上传的 plan 照片)
   → detect_cells(): 墨迹投影找 2 行 × 5 列，不是恰好 2×5 就 PlanError
   → build_view_plan(): 按该 view 的 screen_slots 重排 + 写 caption
   → 缓存 data/assets/viewplans/viewplan-{plan_digest}-{view}.png
```

当前磁盘上（plan digest `c2b0d951f05a3144`）：

```
viewplan-c2b0d951f05a3144-p2_open_hands.png     1288×884
viewplan-c2b0d951f05a3144-p3_right_hand.png     1288×456
viewplan-c2b0d951f05a3144-p4_thumb_visible.png  1288×884
viewplan-c2b0d951f05a3144-p5_left_hand.png      1288×456
```

缓存键是**内容 digest 而非 mtime**：编译产物会成为 provider 输入，
发一张过期的 view-plan 就等于渲染错误的甲序。

若检测失败 → 回落到原始 plan，cell 继续渲染（缺 hand model 则阻断）。

### 8.3 snapshot

queue 时冻结到 `task_snapshots.snapshot_json`（`snapshot_version=1`），字段：

```
channel  contracts  extra  input_assets  negative_prompt
output_type  prompt  prompt_version  size  snapshot_version  style
```

`tk_47e7d1a54d` 实测：`prompt` 5698 字符，含
「Image 1 is the VIEW PLAN … Copy each tile onto the finger its caption names」；
`input_assets` 两项，**第一项是原始 plan `ref-c2b0d951f05a.jpg`，`kind` 标为 `hand_model`**。

### 8.4 worker

```
claim task
  → references = _resolve_matrix_references(task, log)      ← 执行时实时解析，读当前磁盘+DB
  → prompt = task["prompt"]                                  ← 来自 queue 时冻结的文本
  → 若 expected_reference 但 references 为空: strip_reference_block(prompt)
  → reserve spend  →  record_execution(...)  →  provider.generate(request)
  → settle（成功）/ release（ProviderError，不计费）
  → heuristic QA  →（可选）LLM QA  →  review_state
```

**关键事实：prompt 文本走 snapshot，reference 图像不走 snapshot。**
`worker.py:183` 取 `task["prompt"]`（冻结）；而 `worker.py:616` 调
`_resolve_matrix_references`，在执行时按当时的代码 + 当时的磁盘状态重新解析 Image 1。
这就是第 9 节第 1 条冲突的根源，也是本会话 $0.76 白花的直接原因。

`record_execution` 存：`resolved_assets`、`prompt_sha256`、`model`、`provider`、
`prompt_differs_from_snapshot`（恒 `None`）。**不存任何代码/build 身份。**

## 10. 未验证假设

1. **view-plan 能提升摆位准确率 —— 完全未验证。** 没有任何真实 cell 在 view-plan
   生效的 worker 上渲染过。这是当前最重要的未知。
2. **底色即摆位。** `check_nail_placement.py` 只读底色（奇数=绿、偶数=金），
   不读花纹、钻数、波浪方向。底色 10/10 的 cell 仍可能花纹全错。
3. **5/10 是随机基线。** 5 绿 5 金随机分配到 5 绿 5 金的期望命中是 5 —— 这是数学推导，
   不是实测分布；未做置换检验，也未估 per-tone 方差。
4. **mask 极性。** 假定 alpha>128 即甲面内部。`nail-01` 已核对 bbox 一致，其余 119 个 slot 未逐一核对。
5. **输出与 base 几何对齐。** 测量脚本假定输出可整体缩放到 mask 空间。
   1–2px 差异下成立；`2224×1664` 那张未验证。
6. **QA 分数不能作为摆位证据。** LLM QA 给 `tk_47e7d1a54d` 打 100，
   而实测底色摆位 6/10。QA 需要自己识别哪颗甲是哪颗，因此它对摆位的判断不是独立证据。
7. **p3/p4/p5 的 view-plan 正确性。** 4 个编译产物都在磁盘上、尺寸合理，
   但只有 p2 有真实渲染数据。p3/p5 是 1288×456（单手 5 格），未经真实渲染检验。
8. **失败任务是否真的被计费。** 5 条 `failed` 任务有 settled reservation。
   究竟是 provider 真的计费了、还是 settle/release 逻辑有误，未查证。

## 12. 不可违反的约束

以下五条为交接时确认的硬约束。**当前代码对其中三条并不满足**，已逐条标注真实状态。

### 约束 1：Worker 必须仅依据 task snapshot 执行

**当前状态：不满足（部分）。**
prompt 文本来自 snapshot（`worker.py:183`，正确）；
但 reference 图像在执行时实时解析（`worker.py:616` → `_resolve_matrix_references`），
不来自 snapshot。这使 snapshot 与实际输入可以任意漂移——本会话已实际发生（冲突 1）。
在修复前，**snapshot 不能被当作「这次渲染实际用了什么」的凭据**；
实际输入只能从 `task_executions.resolved_assets` 读。

### 约束 2：未经明确确认不得调用付费 Provider

**当前状态：机制满足，需人工遵守。**
付费 e2e 测试由 `RUN_REAL_E2E=1` 显式门控；reservation/budget/breaker 对图像链路有效。
**但 LLM QA 完全在成本体系之外**（冲突 3），会随任务自动触发，不经任何确认。
本次交接后 worker 已停止，队列为空，无任何在途付费调用。

### 约束 3：当前配置变化不得改变已排队任务

**当前状态：不满足（部分）。**
prompt / size / model 已冻结在 snapshot，配置改动不影响它们。
但 reference 解析读执行时的 DB 与磁盘状态：改 `styles.plan_image_path`、
换 active profile、或替换 `data/assets/viewplans/` 下的文件，都会改变已排队任务的实际输入。
**mx-1 与 mx-2 之间的 Image 1 差异正是由数据变化而非代码变化造成的**
（`plan_image_path` 从空变为已填）。

### 约束 4：Nail Slot mask 使用 canonical 坐标

**当前状态：存储侧满足，消费侧需缩放。**
canonical 空间 = **1448×1086**，即 base 照片的像素空间。
`hand_models.width/height`、mask PNG 尺寸、`hand_model_slots.bbox_*` 三者一致。
mask 语义：**指甲在 alpha 通道，RGB 全 0；`convert("L")` 会得到全空 mask。**
**provider 输出不在 canonical 空间**（1449×1085 / 1450×1085 / 2224×1664），
任何用 mask 读写输出的代码都必须先缩放到输出尺寸（冲突 4）。

### 约束 5：新旧 Worker/build 必须可识别

**当前状态：不满足。**
`task_executions` 不记录 git SHA、进程启动时间或 build 标识；
`prompt_version` 来自 queue 时的代码，**不反映渲染时的代码**。
本会话的失效运行在 DB 中与一次正常 mx-2 渲染无法区分。
**在补上 build 身份之前：任何改动 worker 代码后的付费运行，
必须先重启 serve 并核对 `ps -o lstart` 晚于代码 mtime。**
